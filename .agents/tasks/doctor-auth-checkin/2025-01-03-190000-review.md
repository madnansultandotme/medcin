# Doctor authentication and patient check-in with automated commission

Center admins provision doctor accounts with temporary passwords. Doctors must reset password on first login before accessing dashboard. Check-in/out validates booking ownership and calculates commission automatically based on admin-configured rates (percentage or fixed). Device tracking alerts on new logins and requires OTP verification for untrusted devices.

Implementation delivers backend APIs, database schema, web UI for doctors (dashboard, bookings, password change), and admin commission endpoints. Google OAuth partially configured. Mobile not implemented. Build not run (missing dependencies per verification note).

**Watch for:** Password reset redirect broken (middleware.ts missing), Google OAuth callback route missing, device tracking headers not sent by clients, center check-in allows backdated appointments, crypto import missing in doctor checkout.

**Verdict**: NEEDS_CHANGES

## High-level view

Password enforcement mechanism broken. Doctor layout checks passwordResetRequired flag and redirects to /doctor/change-password based on current pathname, but reads pathname from headers().get('x-pathname') that's supposed to be injected by middleware.ts at project root. That file doesn't exist. Redirect logic cannot determine which page doctor is accessing.

Check-in authorization sound. Doctor routes validate booking.doctorId matches authenticated doctor (403 if not). Center routes verify booking.doctorId belongs to center by joining doctors table and checking doctor.centerId. Both validate status transitions (CONFIRMED → checked in → checked out → COMPLETED). Doctor route enforces booking.date === today, center route does not.

Commission calculated correctly for PERCENTAGE (price * rate / 100) and FIXED (fixed amount) modes. Platform takes commission from booking price, center receives remainder. Utility function centralizes logic, used by doctor checkout. Center checkout has inline calculation matching utility. Both handle independent doctors (centerId=null) by skipping commission.

Device tracking expects client to generate UUID and send via X-Device-ID header. lib/device-id.ts has getOrCreateDeviceId() for localStorage UUID generation but no client code calls it or adds headers to fetch. trackDevice() throws error if header missing. First authenticated request after deployment will fail.

OAuth configured in Better Auth (google provider with clientId/Secret, redirectURI pointing to /api/auth/callback/google) but callback route doesn't exist. Design requires manual account linking to verify doctor profile exists before creating session, preventing unauthorized self-registration. Without callback, OAuth flow breaks after Google redirects back.

## Password reset enforcement mechanism

Doctor layout (app/doctor/layout.tsx) server component calls checkFirstLogin() from lib/middleware/first-login-check.ts, gets {requiresReset, user}, reads pathname from headers().get('x-pathname'), defines allowedPaths = ['/doctor/change-password', '/api/auth/change-password-first-login', '/auth/signout', '/api/auth/signout'], redirects to /doctor/change-password if requiresReset && !isAllowedPath.

The x-pathname header should come from Next.js middleware.ts at project root:

```typescript
export function middleware(request: NextRequest) {
  const requestHeaders = new Headers(request.headers);
  requestHeaders.set('x-pathname', request.nextUrl.pathname);
  return NextResponse.next({ request: { headers: requestHeaders } });
}

export const config = { matcher: '/doctor/:path*' };
```

Verification confirms middleware.ts doesn't exist. Without it, headers().get('x-pathname') returns null, pathname defaults to '', isAllowedPath logic breaks. Redirect either fires unconditionally or never fires depending on how empty string matches allowedPaths.

Password change page exists (app/doctor/change-password/page.tsx), API endpoint exists and works correctly (/api/auth/change-password-first-login), but gate keeping mechanism is non-functional.

checkFirstLogin() implementation correct: queries users table for passwordResetRequired flag, returns boolean. Problem is purely pathname detection.

## Check-in and check-out flows

Doctor checkin (POST /api/doctor/checkin): requireDoctor() auth, getUserDoctorId() to get doctorId, validate bookingId in request, fetch booking, verify booking.doctorId === doctorId (403 if not), verify status === 'CONFIRMED' (400 if not), verify checkedInAt === null (400 if already checked in), verify booking.date === new Date().toISOString().split('T')[0] (400 "Can only check in patients for today's appointments"), update booking set checkedInAt=now, checkedInBy=user.id.

Doctor checkout (POST /api/doctor/checkout): requireDoctor(), getUserDoctorId(), fetch doctor with center join, validate booking belongs to doctor, verify checkedInAt !== null (400 "Patient must be checked in before checkout"), verify checkedOutAt === null (400 if already checked out), determine finalPrice = actualPrice || booking.price, call calculateCommission(finalPrice, center) if centerId exists, update booking set checkedOutAt=now, checkedOutBy=user.id, status='COMPLETED', price=finalPrice, commissionAmount, centerEarnings, commissionStatus='CALCULATED', create notification for center admin with commission amount.

Center checkin (POST /api/center/checkin): requireCenter() auth, getUserCenterId(), validate bookingId, fetch booking, fetch doctor record, verify doctor.centerId === centerId (403 "This booking does not belong to your center"), verify status === 'CONFIRMED', verify checkedInAt === null, update booking. No date validation—centers can check in patients for past or future appointments.

Center checkout (POST /api/center/checkout): requireCenter(), validate checkedInAt !== null, validate checkedOutAt === null, fetch center commission settings, calculate commission inline (matches utility logic), update booking with same fields as doctor checkout.

Date validation asymmetry: doctor enforces today, center doesn't. If policy is centers need flexibility for corrections, document it. If not, add validation.

Authorization verified: doctor routes check booking.doctorId matches authenticated doctor's doctorId via getUserDoctorId(). Center routes join doctors table to verify booking.doctorId's doctor.centerId matches authenticated center's centerId. Both use Drizzle parameterized queries (eq(), and() filters), no SQL injection risk.

## Commission calculation

lib/utils/commission.ts exports calculateCommission(price: number, center: CenterCommissionSettings) → {commissionAmount, centerEarnings}:

```typescript
if (center.commissionType === 'PERCENTAGE') {
  commissionAmount = Math.round((price * (center.commissionRate || 0) / 100) * 100) / 100;
} else if (center.commissionType === 'FIXED') {
  commissionAmount = center.fixedCommissionAmount || 0;
} else {
  commissionAmount = 0;
}
centerEarnings = Math.round((price - commissionAmount) * 100) / 100;
```

Math.round() * 100 / 100 ensures 2 decimal precision. Platform takes commission FROM booking, center receives remainder. Example: booking $100, rate 15% → commission $15, center earns $85.

Doctor checkout calls utility after fetching center. Center checkout has inline calculation matching utility exactly. Both routes handle independent doctors (centerId=null) by setting commission=0, centerEarnings=price.

Both routes use finalPrice = actualPrice || booking.price for commission calculation. If doctor adjusts price at checkout (optional actualPrice parameter), commission calculated on adjusted price. If platform wants commission on original price only, should use booking.price always, ignore actualPrice for commission but still update booking.price to actualPrice.

Admin commission update (PUT /api/admin/centers/commission): requireAdmin(), validate with commissionSchema (Zod), update centers table set commissionType, commissionRate (if PERCENTAGE), fixedCommissionAmount (if FIXED), create notification for center admin, send email with new settings.

## Device tracking without client integration

lib/middleware/device-tracking.ts exports trackDevice(userId) → {isNewDevice, deviceId, trusted}:

Reads X-Device-ID and X-Device-Name from headers, validates deviceId is UUID format with regex, queries user_devices table for userId + deviceId match, updates lastUsedAt if exists, creates new record with trusted=false if not exists, returns isNewDevice boolean.

Throws error if X-Device-ID missing or invalid UUID format. Every authenticated request must include header.

lib/device-id.ts exports client-side functions:
- getOrCreateDeviceId(): localStorage.getItem('medcin_device_id') || crypto.randomUUID() + localStorage.setItem
- getDeviceName(): parse navigator.userAgent → "Google Chrome", "Safari", etc
- getDeviceType(): parse user-agent → 'WEB', 'MOBILE_IOS', 'MOBILE_ANDROID'

These functions exist but nothing calls them. Doctor dashboard (app/doctor/page.tsx) and bookings (app/doctor/bookings/page.tsx) use authenticatedFetch() utility (not in this changeset, assumed to exist in lib/utils/authenticated-fetch.ts). That utility needs to import getOrCreateDeviceId(), call it, add headers:

```typescript
headers: {
  'X-Device-ID': getOrCreateDeviceId(),
  'X-Device-Name': getDeviceName(),
  ...
}
```

Without integration, first authenticated API call throws "Device ID is required in X-Device-ID header" from trackDevice().

Device OTP verification (POST /api/auth/verify-device): getAuthenticatedUser(), validate {deviceId, otp} from body, in-memory rate limiting (3 attempts per 10min per deviceId using Map), fetch verification record from verifications table where identifier='device-verify:${deviceId}', check expiresAt, hash submitted OTP with SHA-256 and compare with stored value, update user_devices set trusted=true, delete verification record, clear rate limit.

In-memory rate limit resets on server restart—production should use Redis or database. OTP is 6 digits hashed with SHA-256. sendNewDeviceAlertEmail sends OTP but no error handling if email fails.

## OAuth configuration without callback

lib/auth/server.ts adds to Better Auth config:

```typescript
socialProviders: {
  google: {
    clientId: process.env.GOOGLE_CLIENT_ID!,
    clientSecret: process.env.GOOGLE_CLIENT_SECRET!,
    redirectURI: `${process.env.BETTER_AUTH_URL}/api/auth/callback/google`,
  },
}
```

OAuth flow: user clicks "Continue with Google" → redirects to Google → Google redirects to /api/auth/callback/google with code → callback exchanges code for tokens, verifies user, creates session.

Callback route doesn't exist. Design requires app/api/auth/callback/google/route.ts with manual account linking:
1. Exchange code for tokens via Google token endpoint
2. Verify ID token with OAuth2Client from google-auth-library
3. Extract {email, sub: googleId, name, picture}
4. Query users by email
5. If user exists and role='DOCTOR', verify doctors table has profile (reject if missing)
6. Create or link account in accounts table (providerId='google', accountId=googleId)
7. Update user.googleId and emailVerified=true
8. Create session via Better Auth
9. Set session cookie, redirect to /doctor/dashboard

Without callback, OAuth flow breaks after Google redirects. Better Auth may have default behavior but design requires manual linking to prevent unauthorized doctor accounts.

No Google Sign-In button added to login page. Design requires button redirecting to /api/auth/signin/google (Better Auth's OAuth start endpoint).

## Password hashing

lib/password.ts wraps Better Auth crypto:

```typescript
import { hashPassword as betterAuthHash, verifyPassword as betterAuthVerify } from 'better-auth/crypto';
export async function hashPassword(password: string): Promise<string> {
  return betterAuthHash(password);
}
export async function verifyPassword(data: { password: string; hash: string }): Promise<boolean> {
  return betterAuthVerify(data);
}
```

Doctor provisioning (app/api/center/doctors/provision/route.ts) and password change (app/api/auth/change-password-first-login/route.ts) both use these wrappers. Hashing works, verification works.

'better-auth/crypto' is not documented in Better Auth's public API. If internal module changes export structure in future versions, imports break. Should verify export is stable or use bcrypt directly with config matching Better Auth (check Better Auth source for algorithm, rounds, salt).

Status badges color-coded (green completed, blue checked in, yellow awaiting, gray other). Commission displayed below price for completed bookings.

Doctor layout (app/doctor/layout.tsx): nav bar with "Medcin Doctor" branding, links (Dashboard, Bookings, Profile) conditionally rendered if !requiresReset, user displayed as "Dr. {user.name}", Sign Out link. Wraps children in gray-50 background.
