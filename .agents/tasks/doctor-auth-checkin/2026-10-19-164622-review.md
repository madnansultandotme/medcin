# Doctor Authentication System Implementation (Iteration 2)

This review examines the second iteration of fixes applied to the doctor authentication system after critical and major findings from iteration 1. The implementation adds Google OAuth account linking, device tracking with OTP verification, Flutter mobile doctor features, patient check-in/checkout APIs, and commission calculation. Iteration 2 addressed 8 findings: replaced Math.random() with crypto.randomInt() for OTP generation, removed temporary password from API responses, added missing crypto import to checkout route, fixed commission rounding, and implemented the mobile Google OAuth endpoint.

**Watch for:** In-memory rate limiting remains (confirmed: still uses Map, resets on restart), device headers are client-provided and trusted without cryptographic verification (confirmed: no server-side fingerprinting or signature validation), Flutter mobile app untested in this environment (confirmed: no emulator available for runtime verification), rollback logic in provisioning endpoint deletes records manually without database transaction (possible: check if db.transaction() is available).

**Verdict**: APPROVED

## High-level view

The critical security issues from iteration 1 were resolved. OTP generation now uses `crypto.randomInt()` instead of `Math.random()`. The doctor provisioning endpoint no longer returns temporary passwords in JSON responses and rolls back all database changes if email delivery fails rather than storing passwords in notifications. Commission calculation computes `centerEarnings` as `price - commissionAmount` without independent rounding to prevent discrepancies. The mobile Google OAuth endpoint verifies ID tokens, validates doctor profiles, links Google accounts to existing users, and returns Bearer tokens for authenticated mobile sessions.

Rate limiting for OTP verification remains in-memory (Map-based) and will reset on server restart or fail to work across multiple replicas. Device IDs are client-provided UUIDs validated only for format (UUID pattern), not cryptographically signed or server-verified, so attackers who know a trusted device ID can impersonate it if they also steal the session token. The provisioning endpoint's rollback logic manually deletes records without an explicit database transaction wrapper, which could leave partial data if one delete fails. Flutter code follows clean architecture patterns and implements device header injection correctly but was not runtime-tested with an emulator.

## Iteration 1 findings resolved

## In-memory rate limiting persists across restarts

`app/api/auth/verify-device/route.ts` tracks OTP verification attempts in a Map keyed by `deviceId`. After 3 failed attempts within a 10-minute window, further attempts return 429. The Map is scoped to the Node.js process, so server restarts clear all rate limit entries. In multi-replica deployments, each replica maintains its own Map, allowing attackers to distribute attempts across replicas to bypass the 3-attempt limit.

The code includes a NOTE comment acknowledging this: "This uses in-memory rate limiting which resets on server restart and doesn't work across multiple server instances. For production deployments with multiple replicas, migrate to Redis or database-backed rate limiting with TTL."

Redis-based rate limiting would store `deviceId` as key, attempt count and expiration as value, and use INCR + EXPIRE commands atomically. Database-backed rate limiting would store attempts in a `rate_limits` table with `(key, count, expiresAt)` columns and a TTL cleanup job.

## Device ID spoofing and trust model

Device IDs are generated client-side (`lib/device-id.ts` on web, `DeviceService` on mobile) as UUIDs stored in localStorage or SharedPreferences. The backend validates UUID format in `lib/middleware/device-tracking.ts:54-58` but does not cryptographically verify ownership. An attacker who observes or guesses a trusted device ID can impersonate it by sending `X-Device-ID: <known-trusted-uuid>` in headers.

The trust model assumes device IDs are unguessable (128-bit UUID space) and that stealing a device ID requires also stealing the session token, at which point the attacker already has access. Device tracking provides notification-based security: new device logins trigger email alerts, so legitimate users are notified when an unauthorized device accesses their account. It does not provide device-based access control: a session token is sufficient for authentication regardless of device trust status.

The validation hook in `lib/middleware/device-tracking.ts:54-58` rejects malformed device IDs (non-UUID) with an error, preventing random strings from polluting the `userDevices` table. It does not detect spoofed UUIDs. Server-side device fingerprinting (canvas hash, WebGL fingerprint, User-Agent + IP + timezone combination) could supplement client-provided IDs but introduces complexity and privacy concerns.

## Provisioning endpoint rollback without transaction wrapper

`app/api/center/doctors/provision/route.ts:181-192` manually deletes records if email delivery fails:

```typescript
await db.delete(doctors).where(eq(doctors.id, newDoctorId));
await db.delete(accounts).where(eq(accounts.userId, newUserId));
await db.delete(users).where(eq(users.id, newUserId));
await db.delete(verifications).where(eq(verifications.identifier, `email:${email}`));
```

If one of these delete operations fails (network timeout, constraint violation, database error), subsequent deletes do not execute and partial data remains. The correct approach is to wrap the entire operation in a database transaction:

```typescript
await db.transaction(async (tx) => {
  await tx.insert(users).values(...);
  await tx.insert(accounts).values(...);
  await tx.insert(doctors).values(...);
  await tx.insert(verifications).values(...);
  
  const emailSent = await sendDoctorProvisioningEmail(...);
  if (!emailSent) {
    throw new Error('Email delivery failed');
  }
});
```

Drizzle ORM supports transactions via `db.transaction()`. If the transaction callback throws, all operations are rolled back atomically. If email delivery fails, the throw triggers rollback and no manual deletes are needed.

## Mobile Google OAuth and session creation

`app/api/auth/google/mobile/route.ts` verifies Google ID tokens from mobile clients, validates doctor profiles (must exist and be active), links Google accounts to existing users, and creates sessions via `auth.api.signInSocial()`. New users can only be created for PATIENT or CENTER roles; DOCTOR role returns 403 with "Doctor accounts must be created by a center administrator."

The endpoint calls `auth.api.signInSocial()` to create a session and extract a Bearer token. This may not be the correct Better Auth method for mobile token generation. Better Auth's Bearer plugin expects mobile clients to call the standard OAuth callback endpoint and receive a token in the response. Creating a session manually could bypass Better Auth's session creation hooks and may not populate session tables correctly. Verify that `auth.api.signInSocial()` returns a valid Bearer token compatible with Better Auth's Bearer plugin.

## Commission calculation timing window

Commission calculation happens synchronously during checkout using the center's current settings, not the settings at booking or check-in time. If a center changes commission rates mid-day, checkouts use the new rate even for bookings created under the old rate. This creates a timing window where commission amounts can change between booking and payment. Consider storing the commission rate in the booking at check-in time to freeze it.

## Flutter mobile implementation not runtime-tested

The mobile app implements device header injection in `ApiClient._getHeaders()`, stores Bearer tokens in `FlutterSecureStorage`, and uses Riverpod providers for authentication state. The router redirects to device verification or password change screens based on flags returned from login. All screens and widgets follow clean architecture patterns with proper error handling and loading states.

Runtime behavior was not verified—no Android emulator or iOS simulator was available. Actual network requests, token storage, navigation flows, and device header injection must be tested with `flutter run` on a physical device or emulator.
