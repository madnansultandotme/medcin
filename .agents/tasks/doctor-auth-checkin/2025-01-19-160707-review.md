# Doctor Authentication and Check-In System

Three-phase implementation adding Google OAuth, device tracking, and Flutter mobile support to a Next.js healthcare platform. The platform is commissioned with per-booking center payments. Doctors can be center-affiliated or independent, and must check patients in/out of appointments with automatic commission calculation.

This phase completes Google OAuth account linking (FEAT-001), wires device tracking into the login flow (FEAT-002), and implements the Flutter mobile doctor experience (FEAT-003). Prior work established doctor provisioning, first-login password reset, and check-in/out APIs with commission calculation.

**Watch for:** Math.random() used for security tokens (confirmed: OTP generation), missing crypto import in one route (confirmed: checkout route), device header injection not enforced at middleware layer (confirmed: client-side responsibility), Flutter mobile untested (confirmed: no emulator in review environment), temporary password exposure in API response and email fallback notification (confirmed: returned in JSON and fallback notification).

**Verdict**: NEEDS_CHANGES

## High-level view

Better Auth handles Google OAuth with account linking configured to match emails and block non-provisioned doctors through a validation hook. Device tracking runs client-side after login: the client calls `/api/auth/check-device`, the backend checks the `userDevices` table, and if the device is new or untrusted it generates a 6-digit OTP via `Math.random()`, hashes it with SHA-256, stores it in `verifications`, and emails it to the user. The client redirects to a verification page where the OTP is submitted, verified by re-hashing and comparing, and the device is marked trusted.

Commission calculation applies the center's percentage or fixed rate to the booking price on checkout. Independent doctors (no `centerId`) receive the full amount. Device IDs come from `lib/device-id.ts` on web (stored in localStorage as UUID) and from `DeviceService` on mobile (stored in SharedPreferences). The Flutter app uses clean architecture with Riverpod providers, injecting `X-Device-ID` and `X-Device-Name` headers on every API call via an `ApiClient` interceptor. Google Sign-In on mobile calls `/api/auth/google/mobile`, which is referenced but not implemented.

OTP generation uses `Math.random()`, which is not cryptographically secure and can be predicted. Rate limiting for OTP attempts is in-memory (Map), so it resets on server restart. The doctor provisioning endpoint returns the temporary password in the JSON response body, visible in logs and network traces. If email delivery fails, the temporary password is written to a notification in the database, accessible to center admins but not automatically secured.

## Google OAuth account linking and doctor validation

Better Auth is configured with Google as a social provider in `lib/auth/server.ts`. Account linking is enabled with `trustedProviders: ['google', 'email-password']` and `allowDifferentEmails: false`, ensuring that Google sign-ins only link to accounts with matching emails. The `user.validateUserInfo` hook checks if the user already exists (via `findUserByEmail()`), and if the existing user has role `DOCTOR`, it calls `validateDoctorProfile()` to confirm a doctor record exists. If no doctor profile is found, the hook returns an error preventing sign-in. For new users signing in with Google, the hook allows patients and centers to proceed (role is unknown at this stage) but doctors must be provisioned first by a center admin, so the lack of an existing user record effectively blocks unprovisioned doctor sign-ins.

Better Auth handles the OAuth flow natively: clicking "Sign in with Google" calls `authClient.signIn.social({ provider: 'google' })`, which redirects to `/api/auth/signin/google`, then to Google's consent screen, then back to `/api/auth/callback/google`. The callback route is handled by Better Auth's `[...all]` catch-all route. If account linking succeeds, `googleId` is set in the `users` table and an entry is created in `accounts` with `providerId: 'google'`. The user is redirected to the dashboard appropriate for their role.

Doctor validation happens synchronously in the hook, blocking the OAuth flow if the profile check fails. This prevents a timing gap where a non-provisioned doctor could sign in before validation runs. The `google-auth-helper.ts` utility queries the `doctors` table by `userId`, returning the doctor record or null. If null and the user is a doctor, the error message is "Doctor profile not found. Please contact your center administrator."

## Device tracking flow and OTP verification

Device tracking starts when the client calls `POST /api/auth/check-device` immediately after login. The client sends `X-Device-ID` (a UUID stored in localStorage on web or SharedPreferences on mobile) and `X-Device-Name` (browser or device model). The endpoint calls `trackDeviceLogin()`, which calls `trackDevice()` from the device-tracking middleware.

`trackDevice()` queries `userDevices` for a record matching the `userId` and `deviceId`. If found, it updates `lastUsedAt` and returns `{ isNewDevice: false, trusted: <boolean> }`. If not found, it inserts a new record with `trusted: false` and returns `{ isNewDevice: true, trusted: false }`.

If `isNewDevice` is true or the device is untrusted, `trackDeviceLogin()` generates a 6-digit OTP using `Math.floor(100000 + Math.random() * 900000)`, hashes it with `crypto.createHash('sha256')`, stores the hash in the `verifications` table with identifier `device-verify:${deviceId}` and a 10-minute expiration, and sends an email to the user with the plaintext OTP. The email includes the device name, device type, and IP address (if available). The function returns `{ requiresVerification: true }`.

The client receives the response and, if `requiresVerification` is true, redirects to `/doctor/verify-device?deviceId=${deviceId}`. The page displays a 6-digit OTP input. When submitted, the client POSTs to `/api/auth/verify-device` with `{ deviceId, otp }`. The endpoint fetches the verification record, checks expiration, hashes the submitted OTP with SHA-256, compares it to the stored hash, and if they match, updates `userDevices` to set `trusted: true` and deletes the verification record.

Rate limiting is enforced in-memory: a Map keyed by `deviceId` tracks attempt counts and reset times. After 3 failed attempts within a 10-minute window, further attempts are rejected with a 429 status. On success, the rate limit entry is deleted.

## OTP generation uses Math.random

`lib/auth/track-device.ts:42` and `app/api/auth/request-device-otp/route.ts:65` generate OTPs with `Math.floor(100000 + Math.random() * 900000)`. `Math.random()` is not cryptographically secure: it uses a pseudorandom number generator that can be predicted if the seed is known or guessed. An attacker observing multiple OTPs or timing server initialization could potentially predict future OTPs.

The OTP is hashed with SHA-256 before storage, so database compromise does not reveal the plaintext OTP. However, the weakness is in generation, not storage. If an attacker can predict the OTP, they can bypass device verification.

The correct approach is to use `crypto.randomInt(100000, 1000000)`, which uses a cryptographically secure random number generator. This function is available in Node.js 14.10.0+ and returns an integer in the range [min, max).

## Temporary password exposure in API response and notification

The doctor provisioning endpoint (`app/api/center/doctors/provision/route.ts`) generates a temporary password with `crypto.randomBytes(16).toString('base64url')`, hashes it, stores the hash in the `accounts` table, and sends it via email. The endpoint also returns the temporary password in the JSON response body:

```json
{
  "success": true,
  "doctor": {
    "tempPassword": "xyz123..."
  }
}
```

This temporary password appears in network logs, server logs, and HTTP responses visible to browser extensions or proxies.

If email delivery fails, the code creates a notification for the center admin with the message: `Doctor ${name} (${email}) was created, but the email failed to send. Please manually provide credentials: Temp Password: ${tempPassword}`. This notification is stored in the `notifications` table in plaintext and is visible to anyone with access to the center admin's notification feed.

Better approach: Remove `tempPassword` from the JSON response. If email fails, log the error and create a notification that says "Email failed. Please re-provision the doctor or contact support." Optionally, provide a "Resend credentials" button that regenerates a new temporary password.

## Commission calculation and checkout flow

The checkout endpoint (`app/api/doctor/checkout/route.ts`) accepts `{ bookingId, actualPrice? }`. It validates that the booking belongs to the doctor, has been checked in, and has not been checked out. It determines the final price, fetches the center's commission settings, and calls `calculateCommission()`.

`calculateCommission()` in `lib/utils/commission.ts` handles two commission types:
- `PERCENTAGE`: `commissionAmount = Math.round((price * rate) / 100 * 100) / 100`
- `FIXED`: `commissionAmount = fixedCommissionAmount`

It then calculates `centerEarnings = Math.round((price - commissionAmount) * 100) / 100`.

The rounding approach rounds commission to 2 decimal places, then rounds center earnings separately. This can introduce a 1-cent discrepancy if intermediate rounding changes the sum.

After calculation, the booking is updated with `status: COMPLETED`, `commissionAmount`, `centerEarnings`, `commissionStatus: CALCULATED`, `checkedOutAt`, and `checkedOutBy`. A notification is created for the center admin.

## Device header injection on web and mobile

Web clients inject device headers via `lib/utils/authenticated-fetch.ts`, which wraps `fetch()` and calls `getOrCreateDeviceId()` and `getDeviceName()` from `lib/device-id.ts`. Mobile clients inject device headers via `ApiClient` in `mobile/lib/services/api_client.dart`.

Device headers are client-provided and not cryptographically signed. An attacker can spoof any device ID or name. The backend trusts these headers to identify devices and enforce OTP verification. If an attacker knows the device ID of a trusted device, they can impersonate it and skip OTP verification.

The device tracking middleware validates that `deviceId` matches UUID format and throws an error if malformed. It does not validate `deviceName` or `X-Device-Type`. The trust model assumes that device IDs are effectively unguessable (128-bit UUID space) and that an attacker cannot steal a device ID without also stealing the session token.

## Flutter mobile architecture and provider state

The mobile app follows clean architecture: `data` layer (repositories, datasources, models), `domain` layer (entities, use cases), `presentation` layer (screens, widgets, providers). Riverpod `StateNotifier` providers manage authentication and bookings.

`DoctorAuthProvider` tracks authentication state. Login flow:
1. User submits email/password
2. Provider calls `DoctorAuthRepository.login()`, which POSTs to Better Auth endpoint
3. Repository stores token in `FlutterSecureStorage`
4. Repository calls `/api/auth/check-device` to check device trust
5. If `requiresDeviceVerification` is true, provider sets flag and returns
6. Otherwise, provider fetches doctor profile
7. If `passwordResetRequired` is true, provider sets flag
8. Provider updates state to authenticated

The router redirects based on state: if device verification needed, show OTP screen; if password reset needed, show password change screen; otherwise, allow dashboard access.

Google Sign-In on mobile calls `GoogleAuthService.signInWithGoogle()`, which gets an ID token from the `google_sign_in` package, then POSTs to `/api/auth/google/mobile` with the token. This endpoint is referenced but not implemented.

## Missing crypto import in checkout route

`app/api/doctor/checkout/route.ts:138` references `crypto.randomUUID()` when creating a notification, but the file does not import `crypto`. This will cause a ReferenceError at runtime. The fix is to add `import crypto from 'crypto';` at the top of the file.

## In-memory rate limiting does not persist

OTP verification rate limiting is implemented in `app/api/auth/verify-device/route.ts` with an in-memory Map. This Map is local to the Node.js process. If the server restarts, the Map is cleared and rate limits are reset. If the application is deployed with multiple replicas, each replica has its own Map, so an attacker can distribute attempts across replicas to bypass the limit.

Rate limiting should be stored in Redis or the database. Redis is preferred for short-lived rate limit windows because it supports TTL and atomic increment operations.
